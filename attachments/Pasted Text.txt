A state can run this. You still prototype it with two hospitals; the architecture is what you defend as statewide.
U-HRES at state scale is a state Health Information Exchange: hospitals keep records; the state node holds identity, facilities, consent, routing, and audit. That matches Nigeria’s multi-HIE idea (state HIE + shared APIs + FHIR).

4. Data flows a state actually uses
1. Registration (ADT) Hospital registers/updates patient → adapter sends FHIR Patient + identifier → CR matches or creates UHID → RLS notes “facility X has this patient.”
2. Emergency pull (the demo) Clinician at B searches → CR returns candidates → confirm → Gateway checks consent/treatment relationship → queries A and B FHIR → returns summary → AuditEvent.
3. Discharge push A posts Composition / DocumentReference (discharge) targeted at B or the patient’s primary PHC.
4. Referral ServiceRequest + supporting info; B acknowledges.
5. Public health (later) Scheduled bulk export of de-identified FHIR to the state warehouse. Identifiable queries stay on the exchange with legal basis.

5. Information model (minimum statewide dataset)
Not the whole EMR. A state care summary:
	•	Patient (demographics, NIN if any, contacts)
	•	Allergies
	•	Medications (active)
	•	Problems / conditions
	•	Encounters (last 12–24 months)
	•	Key labs / vitals
	•	Immunizations
	•	Consent
	•	Provenance (which facility asserted what)
Encode as FHIR R4. When Nigeria Core / DHIN profiles exist for a resource, constrain to them.

7. Security model a state can defend
Trust domain: only onboarded facilities with:
	•	Registered org in FR
	•	Client certificate or private-link
	•	Named DPO contact
	•	Data-sharing agreement (state + facility)
Request path:
	1	Clinician authenticates at home hospital (or state IdP).
	2	Hospital token exchanged at gateway for a constrained access token: org, practitioner, purpose, patient (after match).
	3	Gateway enforces: facility active, role allowed, consent or break-glass, minimum necessary categories.
	4	Downstream FHIR calls use service credentials, not the clinician’s password.
	5	Audit writes before the response is returned.
Network: state government network / SD-WAN / site-to-site VPN. Public internet only with mTLS and IP allowlists. PHCs with bad internet get store-and-forward adapters, not chatty live FHIR.
NDPA 2023: health data is sensitive; legal basis = care + consent (and emergency exception you document). Prototype uses synthetic data; production needs DPIA, NDPC registration posture, retention schedule.

9. Facility onboarding (product, not an afterthought)
A state lives or dies on this checklist:
	1	Facility appears in FR (code, type, LGA).
	2	Technical contact + certificate.
	3	Adapter: FHIR R4 or HL7 v2 feed.
	4	Test Patient + test encounter accepted.
	5	Two-way query in staging.
	6	Go-live: ADT on, summary query on, break-glass trained.
	7	Quarterly access review.
Admin console screens: Onboard, Certs, Feeds health, Match queue, Break-glass review.

10. What you implement in the final-year product vs later
Now (still “state architecture,” runnable)

	•	Two hospital FHIR nodes
	•	Gateway: search, confirm, summary, consent, break-glass, audit
	•	Clinician portal + admin (facilities, match queue, audit)
	•	Seed 20–50 synthetic patients, including name variants
Phase 2 (write as future work, design it now)
	•	Keycloak + SMART on FHIR launch inside an EMR
	•	HL7 v2 adapter
	•	Kafka for ADT
	•	Category-level consent (HIV)
	•	DHIS2 aggregate export
	•	Multi-LGA rollout, HA/DR
Phase 3 (do not promise)
	•	Every PHC, claims exchange, national QHIN-style peering, AI
That phasing is how you claim “a state can use this” without lying about your timeline.

12. One-sentence architecture statement (thesis + pitch)
U-HRES is a state-level federated Health Information Exchange: a client and facility registry plus consent-aware FHIR gateway that lets authorised clinicians retrieve a minimum care summary from source EMRs without centralising full patient charts.
